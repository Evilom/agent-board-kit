# 跨设备共享文件交接

Agent Board 保存任务、公告、消息和小型验收附件。工作过程中产生的中间文件、源码包、媒体或其他大文件应放在所有接手设备都能访问的共享存储中，工单记录可核对的地址与版本。Board 的 `board_artifact` 单件上限为 1 MiB，且须由当前任务拥有者上传；它不是通用文件共享盘。

## 按设备所在网络选择存储

| 设备关系 | 建议存储 | 地址示例 |
| --- | --- | --- |
| 同一可信局域网 | SMB 共享盘 / NAS | Windows `\\nas\Studio\AgentBoard\project\work\<work-id>\<batch>\`；macOS `smb://nas/Studio` |
| 不同局域网 | OSS 等对象存储，或有权限控制的网盘 | `oss://bucket/agent-board/project/work/<work-id>/<batch>/` 或网盘中的同等目录 |

这些是选型建议，不表示 Board 自动创建 SMB 账号、OSS Bucket 或网盘分享。存储位置、容量、备份、保留期和读写权限由存储服务管理。跨网设备无法直接访问 RFC 1918 内网地址；不要为交接方便把 SMB 或管理端口直接开放到公网。若组织已有可信 VPN，也可以通过它访问内网存储。

## 一个工单的文件交接

1. 为工单使用独立目录 `project/work/<work-id>/<batch>/`。`batch` 采用不可变的版本或交接批次名；已发布批次不原地覆盖。
2. 发布者将文件写入新目录，完成后生成 `manifest.json`，每项记录相对路径、字节数和 SHA256；必要时加入用途、生成基线与验收说明。文件写入未完成前不发布清单。
3. 在关联工单消息或公告中写明存储类型、共享根或对象地址、批次相对路径、清单 SHA256，以及取得访问权限的负责人。Board 中不写密码、Token、临时签名 URL 或公开访问密钥。
4. 接收设备先核对工单、批次和清单哈希，复制或读取文件后重算每项 SHA256，再继续执行。找不到文件、权限不足、哈希不符时报告阻塞，不把“有链接”当作交接成功。
5. 后续更新另建批次，明确指出取代哪个版本；按团队保留规则清理旧文件，不由工单完成状态自动删除。

示例清单：

```json
{
  "schema": "agent-board-shared-files-v1",
  "work_id": "work-example",
  "version": "2026-09-29-handoff-v1",
  "files": [
    {"path": "report.pdf", "bytes": 12345, "sha256": "<实际文件的 64 位十六进制 SHA256>"}
  ]
}
```

不要把凭据、Cookie、浏览器 Profile、数据库或未脱敏日志放入共享交接目录。若共享目录需供 Board 知识检索，可由管理员只读挂载一个**明确限定的子目录**并登记为 `documents` 来源；Board 不会由此自动为其他设备分发 SMB 权限，也不应该把整块 NAS 盘暴露给服务容器。

设备资源的 `read_chunk` / `upload_*` 提供有范围与哈希校验的点对点传输，详见[设备生态使用指南](设备生态使用指南.md#大文件传输)。它适合明确授权的单次搬运；持续交接、跨设备断线后仍可读取的文件，应在共享存储中保留版本化副本。原本地 Board 不依赖该存储，继续可单机使用。
